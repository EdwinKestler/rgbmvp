# Web UI/UX change boundary and rollback plan

**Status:** Active — refresh implemented and validated  
**Baseline:** `9d1b104` (`docs: sync ladder priority status with closed/partial/open`)  
**Scope:** presentation and browser interaction only; no protocol changes  
**Networks:** Liquid Testnet, Bitcoin testnet, and Elements/Bitcoin regtest only

Implementation record: [UI_REFRESH.md](./UI_REFRESH.md).

## 1. Purpose

This plan governs the proposed visual and usability refresh of the public lab
pages. It makes the UI work independently reversible and protects the protocol,
security, evidence, and historical phase-closure boundaries.

The refresh may improve information architecture, copy, responsive layout,
accessibility, loading/error states, and the presentation of existing `/v1`
responses. It must not change what the protocol does or what the repository
claims has been proven.

## 2. Scenario mapping

The refresh is presentation work over existing scenarios:

| Scenario | UI responsibility |
|----------|-------------------|
| `U0` | Shared shell, navigation, board, and phase presentation |
| `U1` | Issue/transfer form usability; existing requests only |
| `U2` | Guided value-HTLC workflow; existing actions only |
| `S3` | Present existing RGB-wrap state and verification evidence |
| `R4`–`R6` | Present valid, invalid, and pending verification clearly |
| `C3` | Improve BFA audit input and result presentation |
| `U4` | Preserve public read-only/operator distinction and authorization |

This work does not reopen P1, P2, P3, S3, or U4 closure evidence.

## 3. Hard change boundary

### Allowed without protocol approval

- `web/*.html` presentation, semantic markup, and thin-client JavaScript
- New static files under `web/assets/` such as shared CSS, fonts, icons, and
  non-evidentiary illustrations
- Navigation, copy, responsive layout, accessibility, focus, busy, empty,
  degraded, success, and error states
- Safe DOM rendering of fields already returned by `/v1`
- Client-side prevention of accidental duplicate clicks, provided server-side
  behavior remains authoritative
- Documentation specifically describing the UI and its verification

### Forbidden in the UI refresh

- Changes under `crates/lab-rgb`, `crates/lab-chain`, `crates/lab-btc`,
  `crates/lab-simplicity`, or vendored RGB consensus code
- Changes to transaction construction, seals, commitments, consignments,
  witness extraction, HTLC scripts, covenants, or verification rules
- New or changed `/v1` request/response fields, actions, status meanings, or
  authorization behavior
- Browser-side RGB validation, transaction construction, secrets, wallet keys,
  or swap preimages
- Changes to `artifacts/public/` evidence or closed-phase claims merely to fit
  a design
- Mainnet configuration, language suggesting Mainnet readiness, or Mainnet
  explorer links
- Weakening U4 read-only, Bearer, CORS, path, body-size, rate-limit, or
  redaction controls

If an otherwise desirable design requires an item in the forbidden list, stop
that slice and request separate protocol/API/security approval.

## 4. Implementation isolation

Use small, reviewable commits so rollback does not remove unrelated work:

1. `ui: add shared visual foundation and navigation`
2. `ui: add proof-first public landing and evidence presentation`
3. `ui: improve operator console workflows without API changes`
4. `ui: improve audit, responsive, and accessibility states`

Do not combine protocol, API, evidence, deployment, or dependency changes with
these commits. Before each commit, inspect `git diff --name-only` and confirm
that every changed path is inside the allowed boundary or this documentation.

## 5. Pre-change capture

Before implementation:

1. Confirm the worktree and record the starting revision:

   ```bash
   git status --short
   git rev-parse HEAD
   ```

2. Capture desktop and mobile screenshots of `/`, `/demo`, `/status`, and
   `/audit` from the baseline.
3. Save the current `/v1`, `/v1/security`, `/v1/phases`, and representative
   public swap responses as temporary local comparison fixtures. Never include
   a preimage, key, `.env`, wallet state, or private consignment.
4. Record baseline HTTP status codes for public GETs and protected POSTs.

The baseline for this plan is commit `9d1b104`. If implementation begins from a
later revision, record that exact revision in the implementation handoff; do
not silently keep using the older baseline.

## 6. Acceptance gates before merge or deployment

### Functional parity

- Existing `/v1` requests generated by Issue, Transfer, Verify, Swap, and Audit
  remain byte-for-byte compatible in field names and action values.
- `/`, `/demo`, `/status`, and `/audit` load with API available, slow,
  unavailable, empty, and error states.
- Public swap GET views never display or retain a preimage.
- Public read-only posture is visually clear; protected mutations remain
  protected by U4 and are not presented as anonymous public actions.
- Manifest-backed scenario status and explorer links remain sourced from the
  existing evidence, not hard-coded marketing claims.

### Regression and security

- Existing Rust and Python test suites remain green.
- Axum/U4 security and public-view redaction tests remain green.
- No secret-bearing or runtime files appear in `git status` or the staged diff.
- API-derived values are rendered with text-safe DOM methods or explicit
  escaping; no new untrusted `innerHTML` interpolation.
- External links use safe `rel` behavior.

### Human quality

- Keyboard-only navigation completes all existing browser flows.
- Labels, focus, status announcements, contrast, and target sizes receive a
  WCAG 2.2 AA-oriented check.
- Desktop widths 1024/1440 and mobile widths 320/390 are visually checked.
- Reduced-motion preference is respected for any nonessential animation.
- A newcomer can find live evidence before encountering operator mutations.

## 7. Rollback triggers

Rollback the affected UI commit or deployment if any of these occur:

- A `/v1` request or response compatibility regression
- Mutation controls available in a state that should be read-only
- Preimage, key, token, seed, private consignment, or sensitive runtime data
  appears in the DOM, browser storage, logs, screenshot, or response
- Evidence or network labels become inaccurate or imply Mainnet support
- A closed scenario appears reopened, overstated, or unsupported
- A primary page is unusable with keyboard, mobile layout, or API degradation
- Material increase in client errors or inability to load public proofs
- Security review identifies unsafe DOM insertion or boundary weakening

Cosmetic disagreement alone should normally be corrected with a forward patch;
security, protocol-boundary, evidence-integrity, and broken-flow failures require
immediate rollback.

## 8. Local/source rollback

Prefer a normal revert so history and review evidence remain intact. Never use
`git reset --hard` for this rollback.

1. Identify the UI-only commit or smallest ordered set of UI commits:

   ```bash
   git log --oneline -- web docs/UI_ROLLBACK_PLAN.md
   git show --stat <commit>
   ```

2. Confirm the target contains no protocol or unrelated user changes.
3. Revert newest-to-oldest when reverting multiple dependent commits:

   ```bash
   git revert <newest-ui-commit>
   git revert <older-ui-commit>
   ```

4. Re-run the functional, security, and rendering checks in section 6.
5. Confirm `git diff <baseline> -- crates/ artifacts/public/` contains no UI
   rollback side effects.

For an uncommitted UI experiment, use a reviewed reverse patch or restore only
the explicitly listed UI paths after confirming they contain no user work. Do
not run a broad checkout/reset command.

## 9. Hosted rollback after administrator approval

Publication and resource assignment remain outside this UI implementation. Once
an administrator later authorizes hosting:

### Static host

1. Promote the last known-good immutable deployment, or deploy the source
   revision immediately before the faulty UI commit.
2. Verify `/`, `/status`, evidence links, and cache headers from the public URL.
3. Purge/invalidate only the affected static deployment cache if the provider
   requires it.

### Cloud Run API/static image

The UI refresh should not require a Cloud Run API revision. If a combined image
was nevertheless deployed, route traffic back to the previous known-good
revision without deleting either revision, then verify `/v1/security`, public
GETs, protected POST behavior, CORS, and redaction.

Do not create, promote, or roll back any hosted deployment without the pending
administrator approval and assigned Vercel/Google Cloud resources.

## 10. Rollback verification and incident note

After any rollback:

- Confirm all section 6 security and parity gates.
- Capture the restored pages at desktop and mobile sizes.
- Record failed revision, restored revision, trigger, impact, and verification.
- Preserve closed-phase evidence and do not rewrite artifacts to conceal the
  failure.
- Reindex project memory after indexed-file changes when Redis is available;
  if unavailable, disclose `cache_consulted: false` and rely on repository
  files.

## 11. Go/no-go rule

The UI refresh is safe to implement only while its diff remains within section
3 and every section 6 gate passes. Crossing the protocol, `/v1`, evidence, U4,
or network boundary is an automatic **no-go** until separately reviewed and
approved.
